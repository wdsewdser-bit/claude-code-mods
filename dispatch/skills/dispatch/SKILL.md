# 派发规程（仅根代理，不预加载给执行者）

## 分包与派发判断
- 用户已明确要求尽量使用子代理。普通执行任务的默认动作是派发或续用，主会话负责必要初查、目标与边界、关键判断和验收；不要把“可以派”理解成“默认仍自己做”。确定目标、路径和最小验证后，先交出完整工作包再处理独立事务，不先把执行工作做完。
- 单个代码修改、构建、资料调查、浏览器或产物任务也应优先交对应执行者，不必凑多个包。仅微小操作的派发开销明显更大、关键判断必须主会话做、用户明确要求自己做、额度告警或工具不可用时直接执行；多文件本身不要求并行或升级模型。
- 同一批文件或责任域合成一个完整工作包，由同一执行者完成定位、修改和验证；改同一文件的多项工作放进同一个包。
- 派新的之前先检查已有代理能否续用。并行只用于确实独立且有收益的包，注意端口、数据库、锁、构建目录和共享状态。
- 高风险用短计划和必要的独立审查，不固定追加多层角色。失败后先判断是路线、验证、工具还是环境问题，有新假设才重试。
- 本文件记录用户明确的常规委派偏好，工具允许时主动派发，不每次重新询问是否使用子代理。若更高优先级指令或当前接口仍有不可覆盖的限制，遵守并说明具体限制，不用 Workflow 或外部工具绕过。

## 模型与档位
- 主会话 Opus 5.5 / medium，复杂判断用 high；不把主模型的档位继承当作所有子代理的默认。
- 额度：套餐所有 Claude 模型共用一个额度池；DS（delegate_flash / delegate_pro）不占 Claude 额度。执行默认交给 DS（见“delegate（DS）派发”），含密钥或敏感数据的活也交给 DS（用户 2026-10-18 决定接受该链路）。不用 Sonnet。
- Haiku 5.5 只用于需要 DS 没有的工具（浏览器、LSP、Artifact 等）的执行：worker、worker-ptc、researcher 默认 low（2026-10-20 实测三组题，含 20 多个文件的遗留代码题，low 与 medium 得分相同，省 15–42%；按步自适应升档从未触发，已放弃）；browser-worker、artifact-worker 暂留 high（未覆盖）；判断明显吃力或做过一次不稳时单次覆盖 medium/high，不能跳过必要验证。
- DS 做过一次仍不稳，或需要深度独立审查时，派 Opus 5.5（reviewer 按其定义为 high；worker-ptc / worker 单次覆盖 model=opus 时用 medium）。实测 Opus reviewer 挖得更深但单次成本约为 DS 的 25 倍，只在值得时用。文件多不等于必须升级模型。
- 在 Agent 调用中用实际支持的 model 别名 haiku / opus；档位写在代理定义或单次派发参数里，不设全局 CLAUDE_CODE_EFFORT_LEVEL，也不强制全 Haiku。
- Haiku 未完成时先检查具体缺口；只是漏一项验证就续跑补齐，需要重新判断路线再升级或由 Opus 收回。reviewer / oracle 只在独立审查或重大不确定性有价值时使用。
## 稳定的工具配置

| subagent_type | 默认模型 / 档位 | 工具与用途 |
|---|---|---|
| worker-ptc | Haiku 5.5 / low | 只有 run_code（程序内 read/grep/edit/bash）；Claude 端代码、脚本、配置执行包的默认选择 |
| worker | Haiku 5.5 / low | Read、Grep、Glob、Edit、Write、Bash、LSP；需要 LSP、交互式逐步排查，或 worker-ptc 做过一次仍不稳时用 |
| researcher | Haiku 5.5 / low | Read、Grep、Glob、WebFetch、WebSearch；文件定位和公开资料核查 |
| browser-worker | Haiku 5.5 / high | 文件工具、Bash、Claude_Browser MCP；浏览器交互和视觉验收 |
| artifact-worker | Haiku 5.5 / high | 文件工具、Bash、Artifact；文档、幻灯片、表格和媒体产物 |

- 用同一责任域需要的稳定配置，不给每个小任务生成新类型。worker-ptc / worker 可单次覆盖为 Opus，无需复制一套角色文件。需要 Claude 端执行时默认派 worker-ptc（用户 2026-10-18 决定，仍在适配期，发现问题记下并改提示）。
- 这些配置使用 omitClaudeMd: true。派发包必须传入本任务有关的项目规则、允许路径、权限边界和验收要求；不得用省提示词为理由省掉安全约束。
- 工具池在启动时确定；续用不能靠一条消息获得未授予的浏览器、Artifact 或 Skill 工具。工具范围改变时用对应配置新建并传短交接。
- 选明确的 subagent_type，不用默认全工具 general-purpose；不复制整段主会话作普通 worker；默认关闭 fork。缺少所需工具时报告，不擅自接入新 MCP、安装插件或改权限。

## 子代理固化规则

下面同一段已直接写入六个代理的系统提示，执行者启动即获得这些规则；不依赖派发者每次重新转述，也不要求子代理再读取全局 CLAUDE.md。修改此段时同步六份并验证完全一致。派发包继续补本任务的项目特有约束。

## 通用执行规则

规则版本：20261014-v4。

默认中文，结论和证据先行，只给必要结果、路径、验证与限制；不继续委派。遵守派发包的项目规范、允许路径和授权边界。

## 减少轮次
- 每轮请求都会携带已有上下文，缓存能降低稳定前缀的成本：动手前想好本轮还需要什么，独立的读/查/命令一次发出；依赖前一步结果的保持串行。
- 改动范围明确时先读齐相关文件，再集中修改和验证；多步验收写成一条命令或脚本。
- 共享文件写入串行；注意端口、数据库、锁、构建目录的争用。
- 长命令用 `run_in_background`，不轮询。日志先筛关键字段，完整日志留文件；大日志文件用 `rtk log <文件>`（只留错误、警告和计数），大 JSON 用 `rtk json <文件>`（只看结构和样例值，`--keys-only` 只看键）。
- 公开资料用 WebFetch / WebSearch；登录、交互或视觉验证才用浏览器。
- `node_modules`、`dist`、`build` 等依赖和产物目录可以读写，但只按确切路径定点操作，不整目录扫描或通读。
- `.next`、`coverage`、`__pycache__`、`*.min.js`、`*.min.css`、`*.map` 被内置读写工具屏蔽；用户明确要求时才用命令行定点读（限定范围）、改或删。
- 跨多个文件的批量改写（尤其是正则替换）、大输出需分页、批量复制/移动/删除文件时，可用则优先用 `mcp__ptc-run__run_code`（edit/replace/batch 有过期检查、原子写和回滚；SDK 同步返回，不要链 `.then`）；只读统计用 Bash 脚本或 Grep 即可，单次搜索用 Grep，图片/PDF 用 Read。

## 执行补充
- 已知互不依赖的读查在同一轮批量调用，宿主支持时并行；参数依赖或共享状态争用时串行。批处理不等于并行。长操作按接口支持使用后台或早返回，记录任务 ID 并等真实结果，不重复提交或把超时当完成。
- 按确切路径、符号或行范围精读；未知位置先在限定目录用 Grep（带行号）、Glob 或 LSP 列出函数和类来定位，再用 Read 的 offset/limit 只读需要的片段，不要整文件读大文件。已有且未变的内容不重读。工具输出设置预算，先筛必要字段、关键错误与来源，不搬运整个对象或日志。
- 最小范围修改，不擅自提交、推送、操作生产、加依赖或改弱测试；危险操作先核对授权并备份。验证匹配影响面并提供真实证据，通过后仅新修改、失败或未解决风险才扩大；未完成或未验证不报 completed。

## 技能按需读取
- 不在通用代理中设置大量 skills 预加载，也不预加载 dispatch、控制器角色或与工作无关的技能。
- 主会话选择当前任务需要的技能，给出确切 SKILL.md 与必要脚本路径；执行者只定点 Read 所需内容，不枚举全部技能目录。
- 普通精简配置不提供 Skill 工具。定点 Read 不等同于 Skill 的参数展开和调用；依赖这些机制时，由主会话加载后传必要内容，或在确需的专门配置中显式加入 Skill。
- skills 字段只控制预加载，不是访问白名单；给代理 Skill 仍可能带来技能目录开销。技能缺失或明确要求某工具时报告实际缺口，不伪称已加载。

## 续用与新建
- 续用启动较早、尚未包含当前 subagent-core 版本的代理时，把本技能的通用执行规则随首次续跑消息补发一次，记录已传版本；以后只传规则差异，不每轮重复。新代理启动时已有正文中的规则，无需额外读取或再复制。
- 同一模块、同模型、前次理解仍有效、上下文相关且缓存温热：优先 SendMessage(to=已有 ID 或名称) 续用，记住续用保留原工具和历史。
- 新工作关系弱、历史里有大量日志或失败尝试、需要独立意见、模型或工具范围要变：考虑新建精简代理，附必要事实和确切位置。
- 比较的是后续完成成本：缓存读取与新写入、重新读文件、输出与思考、主会话交接与验收、返工。已付缓存写入费不是必须续用的理由；过 TTL 后历史仍在，也不是必须重建的理由。
- 同模型、档位、类型、工具和工作目录的稳定前缀可能被新代理共享；首次冷启动和后续热启动分开看，不假定每次新建都要重写全部前缀。
- 本账户订阅保持主会话和子代理 1h 缓存，不根据 API 1h 写入加价切成 5m。缓存是否实际命中看响应 usage，不凭 TTL 配置推断。
- Haiku 的 100K 门槛计入系统、工具、文件和历史；接近或超过只作为比较信号。短交接能省去大量无关历史时重建，有价值的项目理解仍可能值得续用。
- 内置 Explore / Plan 无可续用 ID，预计连续工作优先自定义 researcher / worker。maxTurns 返回 partial 不算完成，必要时续用补齐。

## 任务说明与等待
- 任务说明必须自包含，只写目标、允许读写路径、确切位置或参考模式、已确认事实、相关项目规范与授权、必须完成的验证和停止条件。
- 已知位置就给路径和符号或行号；需探索时限定目录和合理读取范围。长日志先筛关键字段，不让执行者为背景通读全部文件。
- 验证与影响匹配，明确关键检查及运行限制；共享宿主、端口或状态的测试串行。派发后根代理不改、不重复读取或测试执行者的责任域。
- 手头有独立工作时用当前接口支持的后台执行；否则等真实结果。记录 agent ID，不催进度、不反复列表、不把超时或 interrupted 当完成。

## 终态与验收
- 任务说明要求返回 TASK_TERMINAL: completed|blocked|failed；最多 5 项改变决策的发现，附改动路径、实际验证、剩余风险和必要位置清单。
- completed 必须代表目标已实现且必要验证完成；未运行的检查和 partial 明确标出。需要交接时附不超过 10 行的已确认事实与未解决点。
- 合格证据直接验收，关键结论按风险抽查；仅具体缺口才补检查或续跑，不重做整个探索。
- 代理持续返回异常时停止派发，由根代理继续，只报告已证实的异常。

## delegate（DS）派发
- 执行任务默认 delegate_flash（effort=low）；需要更多判断时用 delegate_pro（effort=high），effort=max 可选。找隐藏 bug 先派只读诊断（mode=read），确认根因后再 mode=work 修改。默认 mode=read，需要修改或命令时用 mode=work 并写明允许路径。
- 调研开源项目或第三方库：派活前根代理先把对应版本的源码浅克隆到本地（`git clone --depth 1 --branch <tag>`），cwd 指向克隆目录，让执行者在本地批量 grep/read；不要让它用 WebFetch 逐页读 GitHub。只读模式（ptc=only）只能读 cwd 里的文件，所以要读的东西都放进 cwd，别为了读 cwd 外的一个文件传 ptc:off。网页资料让它在程序里用 `tools.fetch({urls:[...]})` 批量抓原文。一个包里只放一两个问题，并写明收敛条件（例如 N 轮内出报告，查不到的写“未证实”）。
- 任务说明自包含，要求精简汇报（结论、改了哪些文件、测试结果）。轮数和时长基本不设限；预计超过几分钟或有独立工作时 background=true，记录 ID，同责任域用 resume。
- 执行包针对 DS（1017）补四点：写明本任务 1–3 条真正要紧的连锁后果（“改了 X，Y 会失效，要核对”）；“做 N 次 / 统计”类要求让它写脚本循环计数，不靠模型自己数；随时间变化的状态（进程、端口、额度、文件）每次决策前重新读取，不沿用开头的快照；关键范围或完成定义有歧义时回报 `TASK_TERMINAL: blocked` 并写明要澄清什么，不自行补规则。必做验证要写明，减少无效调用不能省掉它。
- 超时先核对真实文件与运行状态，不重复提交。工具或凭据错误先按原因处理；无新假设不反复派发，不能恢复时由根代理继续。不主动增加订阅或切换供应商。

## delegate_gpt（GPT）派发
- 额度走 ChatGPT 订阅（当前 Plus，用量有限），既不占 Claude 额度，也不同于 DS 的近乎无限。用户分工（2026-10-23 确认）：DS 做快活和中等难度的活；GPT 负责后端业务实现、复杂代码和独立的代码审查；Opus 主会话负责判断、前端和视觉、验收。
- 默认 model=gpt-6.1-sol。只有高难、高风险的局部问题，例如跨模块疑难故障、关键算法、难以判定的正确性问题，或者 Sol 做过一次仍不稳时，才用 gpt-6-astra，不把它当日常 worker。
- GPT 档位（effort）：最低 medium，不填也按 medium 跑，不用 low。常规后端实现和审查用 medium；判断量较大、跨模块的改动或深度审查用 high；真正高难的问题用 xhigh，一般就够；max 只在 xhigh 做过一次仍不稳时按需使用。没有新假设不加档。
- 适合派给 GPT 的：DS 做不稳或判断量较大的后端改动；需要换一个模型做独立审查的 diff，这时用 mode=read，审查只依据 diff、调用关系和测试，不顺手改代码。机械改写、检索、跑固定命令仍交给 DS flash。
- 执行包要写明：允许修改的路径；禁止的改动（依赖升级、迁移、无关重构或格式化、新增抽象）；验收命令。要求它先围绕验收做最小改动；发现更大的方案只报告权衡，不自行扩大范围。
- 汇报没有测试命令和输出就打回；它自报 PASS 不算验收，根代理要核对真实文件和测试。用法与 DS 相同（mode / background / resume / effort）；CPA 会自动启动，首次调用多等几秒。连接或认证失败时先看 ~/tools/cliproxyapi/cpa.log，不改派到付费 API。
