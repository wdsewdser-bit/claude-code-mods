# SPEC-p2c：交接信息里进行中任务的体积要有边界（astra 审查 P2 第 9 条，只做其中一部分）

## 起因和取舍

审查指出两点：交接信息的 token 上限（`handoffTokens`，15,000）不是硬上限——首页里进行中的任务、最后回复、子代理名单都不裁剪；账本文件没有容量边界，可能撞上引擎 4 MiB 的读写上限。

这里只做第一点里真正会失控的部分，其余不做，理由：

- 超出 15,000 一两成本身不造成任何问题，这个数是成本目标，不是安全线。真正的风险是**没有上界**：进行中的任务越挂越多，每个最多带 3 条共 3,000 字的记录，交接会跟着线性增长。
- 账本文件 4 MiB 相当于几千条记录，已结束的任务会被 `turnPage` 归档；真写不进去时 SPEC-durable 的"写失败看得见"会报出来。现在不为它加分片。

## 改动

位置：`hooks/lib/ledger.ts` 的 `renderHome`（"进行中 / 受阻的任务"一节，约 512–542 行）；`hooks/lib/handoff.ts` 里 `assemble` 上方的注释；`hooks/lib/types.ts` 里 `handoffTokens` 的注释。

1. 进行中 / 受阻的任务按最近一条记录的时间从新到旧排。最近更新的 `MAX_FULL_ACTIVE = 5` 个照现在的样子完整显示（记录、下一步都不变）。
2. 排在后面的任务压成短格式，每个最多三行：
   - 任务行不变：`- <task_id>：<标题>（状态）`
   - `  - 最新 #L<seq>：<正文前 200 个字符>`，被截短时末尾加 `……`
   - 有下一步时 `  - 下一步：<前 200 个字符>`（沿用来的照旧标"沿用 #L 几的记录，可能已过时"）
3. 只要有任务被压短，在这一节末尾加一行：`（还有 N 个较早更新的任务只显示了摘要，完整记录用 ledger_read 按 task_id 查）`。
4. 显示顺序：完整显示的在前，压短的在后；各自内部从新到旧。注意现在的顺序是 `tasksOf` 的"首次出现顺序"，改成从新到旧会改变已有输出的顺序——已有测试里断言顺序的，改断言并在报告里列出。
5. 这只影响首页和交接里的显示。`session.ts` 的 `buildHandoff` 里给"待改位置"取任务的逻辑不动（它有自己的上限）。
6. 注释如实改：`assemble` 上方和 `handoffTokens` 的注释写明这是目标值，开头、首页、最后回复、子代理和工具说明不参与裁剪，所以总量可能超出；进行中任务的体积由 `MAX_FULL_ACTIVE` 约束。

## 测试

- 5 个进行中任务：全部完整显示，没有"只显示了摘要"那一行。
- 8 个进行中任务：最近更新的 5 个完整，另外 3 个是短格式，末尾有说明行且数字是 3。
- 短格式里超过 200 字符的正文被截短并带 `……`；沿用来的下一步仍带来源标注。
- 8 个任务、每个 3 条长记录时，首页的估算 token 数明显小于全部完整显示时（断言一个具体上界即可）。
