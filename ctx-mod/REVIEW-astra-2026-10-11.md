**这条路线值得保留，但当前实现还不能承担“原文可靠保存，所以可以放心丢掉上下文”这个承诺。应先修恢复正确性，再扩大自动换窗。**

它实际上把模型的语义压缩移到了平时写账本的阶段。这样能避免换窗时临时生成摘要，却仍然依赖模型判断哪些事实值得保留。代码能保证格式和编号合法，不能保证账本足以恢复任务。

下面区分三类依据：**代码确认、内存复现、待引擎验证**。“复现”均为调用项目原函数或钩子、使用内存 I/O；没有修改文件、联网或调用模型。开发笔记中的真实会话数据是项目已有证据，本轮没有重新验证。

相对模型摘要，我的判断是：

| 场景 | 判断 |
|---|---|
| 长期编码、反复查日志、精确恢复命令和工具结果 | 很适合，前提是历史确实完整、可检索 |
| 阶段清楚、产物明确、模型持续维护账本 | 通常比临时摘要更可控 |
| 探索、讨论、需求反复变化、重要结论散落在自然语言里 | 更容易丢掉约束、理由和隐含关联 |
| 图片、桌面操作、多代理异步协作 | 当前实现不足，文本历史和代理名单不能替代完整状态 |
| 很短的任务 | 账本工具、提示词和额外维护可能得不偿失 |

实际实现保留了普通 `/compact`、账本不新鲜时的自动压缩等摘要回退路径，这个保底值得保留。见 [register.ts:883](C:/Users/yadaz/.claude/skills/ctx-mod/hooks/register.ts:883)。

以下问题按严重程度排列。

1. **P1：写入失败被当作成功，换窗没有持久化屏障。〔已复现〕**

   队列捕获写入异常后仍然完成 Promise；`record`、`ledgerAppend` 和 `commitSwitch` 都不等待实际写入成功，`flush` 也只等待队列排空。

   我让所有写入抛出 `EIO`，结果仍然返回“已记录 #L1”，窗口推进到 2，`flush` 正常返回，而持久存储为空。归档写失败后继续覆盖当前账本，还会把唯一可恢复的条目移走。

   串行队列也不构成跨文件事务：合并待写的 `meta.json` 保留原排队位置，可能让新 metadata 先于对应历史快照落盘。

   位置：[history.ts:442](C:/Users/yadaz/.claude/skills/ctx-mod/hooks/lib/history.ts:442)、[session.ts:898](C:/Users/yadaz/.claude/skills/ctx-mod/hooks/lib/session.ts:898)、[session.ts:1211](C:/Users/yadaz/.claude/skills/ctx-mod/hooks/lib/session.ts:1211)。

   **应改为：**写入失败可观察；历史、账本持久化成功才允许零摘要换窗；用分代快照和提交清单恢复最后完整版本，不能依赖“退出时 flush”。

2. **P1：旧窗口的第二个及后续分片通常读不到。〔已复现〕**

   位置：[history.ts:94](C:/Users/yadaz/.claude/skills/ctx-mod/hooks/lib/history.ts:94)、[session.ts:522](C:/Users/yadaz/.claude/skills/ctx-mod/hooks/lib/session.ts:522)。

   **应改为：**按分片清单读取，或者一直检查后续编号；文件大小不能作为终止标记。读取失败也不应永久标记整个窗口已加载。

3. **P1：meta 损坏或落后时会重用历史编号。〔已复现〕**

   位置：[session.ts:546](C:/Users/yadaz/.claude/skills/ctx-mod/hooks/lib/session.ts:546)、[tests/session.test.ts:87](C:/Users/yadaz/.claude/skills/ctx-mod/tests/session.test.ts:87)。

   **应改为：**从完整分片清单恢复编号、水位和窗口；区分不存在、损坏与读取失败。不能把所有异常都解释成新会话。

4. **P1：“完整历史”实际缺少若干不可恢复的内容。〔代码确认，部分已复现〕**

5. **P1：账本“新鲜”不能证明可以安全换窗。〔已复现〕**

8. **P2：请求数实际统计的是工具调用数。〔已复现〕**

成本模型目前适合做启发式提示，不适合当作可靠的经济决策。主要假设在 [session.ts:1116](C:/Users/yadaz/.claude/skills/ctx-mod/hooks/lib/session.ts:1116) 和 [usage.ts:66](C:/Users/yadaz/.claude/skills/ctx-mod/hooks/lib/usage.ts:66)：

- “剩余请求数”实际上只有默认 100 和 `expect_more_work:false` 时的 5。
- 重读成本固定使用 6,000 token，没有测量换窗后的实际恢复行为；已有片段还可能被重复计入。
- 没有计算写账本的输出、恢复推理、额外工具往返，以及重新增长的上下文。
- `wRead=0.025` 是配置权重，本项目没有证明它等于订阅额度的真实扣减比例。

比较优化收益时，应同时记录换窗后若干请求的写入、读取、输出和恢复动作，而不只比较交接大小。

可以具体做的效率优化如下：

| 改哪里 | 为什么省 |
|---|---|
| `session.record`、写队列 | 当前每条记录先序列化整个分片，队列合并也省不掉这一步。改为队列真正执行时序列化最新快照；同一分片 n 次更新的累计序列化量可从约 nS/2 降为按批次处理 |
| `ledger_append` | 支持一次提交多项更新，统一校验和持久化。顺序记账可减少往返；原本同轮并行的情况只省信封和重复处理 |
| `renderHome`、`renderWorkset` | 路径相对化、合并重叠片段、删读写次数、压缩已完成列表。每少带 2,000 token、后续 100 次请求，按当前权重少约 5,000 读取当量，另省首次写入；这不是订阅额度承诺 |
| `history` | 批量按编号读取，支持范围和分页；建立编号到分片的索引，避免反复加载、排序整个历史 |
| `session.compact` 的 `precompute` 分支 | 当前直接放行。若宿主触发预计算而随后使用零摘要交接，会浪费摘要请求；在检查点可靠时跳过，具体收益取决于实际触发频率 |
| 系统提示词与全局表 | 保持系统段稳定，跨会话观测表只注入当前相关的少量结果，不把动态数据库拼进系统提示词 |

换窗后最容易丢的，是**任务之间的语义关系**：为什么选这个方案、否定了什么、旧请求里仍有效的约束、验证做到了哪一步，以及正在等待哪个结果。原文存在也不够；新模型必须知道该查哪条。

交接中我会减少：

- 很长的最后回复整段复制。
- “不要重跑同样探测命令”的绝对指令。历史中的服务状态、进程和文件内容可能已经过时，见 [handoff.ts:113](C:/Users/yadaz/.claude/skills/ctx-mod/hooks/lib/handoff.ts:113)。

- 持续有效的约束、已接受决策、关键事实，允许明确取代。
- 检查点覆盖编号、尚未记账的尾部范围。
- 待执行动作和已执行动作的界线，避免重复写入或重复提交。

跨会话长期记忆值得做，但应晚于当前恢复修复。建议只存项目约束、已验证决策、反复有用的事实和明确偏好；每项带来源、作用域、验证时间、版本或文件指纹、失效条件。按项目和当前任务检索少量注入，过期事实退出，冲突显式处理。不要把全部账本自动提升为长期记忆，也不必先引入向量数据库。

对“超过 8 万先换窗再加载”，我的意见是：**可以做受控实验，暂时不应硬编码为普遍规则。**

门槛应看预计失效的消息部分。按开发笔记约 5 万 token 的命中前缀，总上下文 8 万时，旧消息部分只有约 3 万。应比较：

> 避免重写的旧消息成本 + 后续缩短上下文的收益  
> 是否超过新交接、恢复读取、记账输出和额外请求成本。

新增工具定义如果进入未命中部分，也要写入；不能假定换窗后只写几千。笔记中 6.3 万上下文的实例仍写了约 2.9 万，见 [NOTES-dev.md:157](C:/Users/yadaz/.claude/skills/ctx-mod/NOTES-dev.md:157)。

拦截点方面：

- **优先考虑 `tool.call` 中、调用 `next(e)` 之前。** 对明确 `select:` 且命中已确认高成本组的请求，可以先要求完成检查点，再在新窗口重试。
- 关键词搜索无法事先知道精确匹配，需要无副作用的解析能力，或者引擎提供“查询”和“激活”分离接口。
